# RevenueOS — WebSocket Protocol Specification (v1)

## 1. Protocol Overview

The RevenueOS WebSocket protocol provides real-time, bidirectional, structured communication between the browser client and the Django Channels ASGI backend.

### Key Characteristics
- **Version:** `v1`
- **Transport:** WebSocket over TLS (`wss://` in production, `ws://` in local development).
- **Serialization:** Strict JSON format.
- **Envelope Standard:** Uniform structure for all client-to-server requests and server-to-client responses/broadcasts.
- **Request Correlation:** Every client-initiated command carries a unique `requestId` (UUIDv4) that is echoed back in responses.
- **Authentication:** Established during handshake via secure HTTP-only session cookies. Unauthenticated connections are rejected with close code `4401`.

---

## 2. Frame Envelope Standard

### 2.1 Client-to-Server Envelope (Request)
```typescript
interface ClientMessage<T = unknown> {
  protocolVersion: "v1";
  requestId: string;           // UUIDv4 generated by client for correlation
  type: ClientMessageType;     // Command verb
  timestamp: string;           // ISO 8601 UTC timestamp
  payload: T;                  // Bounded payload object
}
```

### 2.2 Server-to-Client Envelope (Response & Event)
```typescript
interface ServerMessage<T = unknown> {
  protocolVersion: "v1";
  requestId?: string;          // Echoed for RPC responses; omitted for broadcast events
  type: ServerMessageType;     // Event or response verb
  timestamp: string;           // ISO 8601 UTC timestamp
  payload: T;                  // Typed payload object
  error?: ProtocolError;       // Present only when type is 'error' or response indicates failure
}

interface ProtocolError {
  code: string;                // e.g., 'UNAUTHORIZED', 'INVALID_PAYLOAD', 'RATE_LIMITED'
  message: string;             // Human-readable, safe error message (no stack traces)
  details?: Record<string, unknown>;
}
```

## 3. Message Type Catalog

### 3.1 Client Message Types (Commands)

| Message Type | Description | Idempotent | Rate Limit |
| :--- | :--- | :--- | :--- |
| `ping` | Heartbeat keep-alive check. | Yes | None |
| `revenue.list` | Fetch paginated list of revenue opportunities ranked by priority. | Yes | 60/min |
| `revenue.details` | Fetch comprehensive detail for a single payment opportunity. | Yes | 60/min |
| `recovery.analyze`| Request Gemini AI analysis and recommendation for a payment. | Yes | 15/min |
| `recovery.execute`| Request execution of an authorized recovery action. | No (Guarded) | 10/min |
| `decision.explain`| Fetch detailed explainability and factor audit for a decision. | Yes | 30/min |
| `metrics.summary` | Fetch real-time aggregate recovery metrics and baseline comparison. | Yes | 60/min |

### 3.2 Server Message Types (Responses & Events)

| Message Type | Description | Scope |
| :--- | :--- | :--- |
| `pong` | Heartbeat response. | Direct RPC |
| `revenue.list.response` | Paginated opportunity list with ERV and priority score. | Direct RPC |
| `revenue.details.response` | Comprehensive opportunity data payload. | Direct RPC |
| `revenue.updated` | Opportunity data mutated (status change, score shift). | Broadcast |
| `analysis.started` | AI analysis task started for an opportunity. | Broadcast/Direct |
| `analysis.completed` | AI recommendation generated and schema-validated. | Broadcast/Direct |
| `recovery.approved` | Policy engine approved the AI recommendation. | Broadcast/Direct |
| `recovery.blocked` | Policy engine blocked the recommendation with violation rules. | Broadcast/Direct |
| `recovery.executed` | Authorized action executed via Razorpay adapter. | Broadcast/Direct |
| `payment.updated` | Payment state updated (e.g., via Razorpay webhook). | Broadcast |
| `decision.created` | New audit ledger entry recorded. | Broadcast |
| `metrics.summary.response` | Aggregated recovery and counterfactual metrics. | Direct RPC |
| `metrics.updated` | Metric aggregates changed due to recovery outcome. | Broadcast |
| `error` | Structured operational or protocol error. | Direct RPC |

## 5. Connection Lifecycle & Resilience

### 5.1 Authentication Handshake
1. Browser initiates WebSocket connection: `GET /ws/v1/app/`
2. Django Channels ASGI middleware inspects the `session_id` cookie.
3. If the session exists in MongoDB `sessions` collection and `expires_at > now`:
   - Connection is accepted.
   - User identity is attached to scope: `scope["user"] = user_doc`.
4. If missing or expired:
   - Connection is rejected with WebSocket close code `4401` (Unauthorized).

### 5.2 Heartbeat & Stale Connection Management
- Client sends a `ping` every **25 seconds**.
- Server responds with `pong` immediately.
- If no ping or activity is received by the server within **60 seconds**, the server closes the socket with code `4408` (Connection Timeout) to reclaim server resources.
- If client receives no `pong` within **5 seconds** of sending a `ping`, the client marks the connection as stale and initiates reconnect.

### 5.3 Exponential Backoff Reconnection Strategy
When disconnected unintentionally, the client client automatically reconnects using jittered exponential backoff:
$$T_{\text{wait}} = \min(T_{\text{max}}, T_{\text{base}} \times 2^{\text{attempt}}) \pm \text{jitter}$$
- $T_{\text{base}} = 1000\text{ ms}$
- $T_{\text{max}} = 30000\text{ ms}$
- $\text{jitter} = \text{random}(0, 500\text{ ms})$
- Max retry attempts: unlimited while tab is active.

### 5.4 Bounded Message Size & Rate Limiting
- **Max Message Size:** Enforced at ASGI consumer level: 32 KB (32,768 bytes). Messages exceeding this size are rejected with error code `PAYLOAD_TOO_LARGE` and the frame is dropped.
- **In-Memory Leaky Bucket Rate Limiter:** Sensitive client actions (`recovery.analyze`, `recovery.execute`) are rate-limited per user session to prevent spamming the Gemini or Razorpay APIs.

## 6. Frontend Client Lifecycle Implementation

The frontend maintains exactly **one** singleton WebSocket connection per session managed by `useWebSocket` hook and `RevenueWebSocketClient` class:
1. `CONNECTING`: Visualized in header with amber indicator.
2. `CONNECTED`: Green indicator, full interactive controls enabled.
3. `DISCONNECTED / RECONNECTING`: Amber pulse indicator, action buttons safely disabled to prevent uncoordinated local mutations.
4. `TERMINATED`: Red indicator (authentication lost, redirects to login).
